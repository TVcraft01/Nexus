## How the phone was made to hear a sentence

I cannot speak, so the acoustic stimulus was synthesized **on the PC** — a
local neural TTS (piper, `en_US-lessac-medium`) run from `/tmp` — and played
out of the laptop's speakers with `paplay` while the phone's microphone was
open. Nothing about it reaches the app: the phone only ever sees a room with a
voice in it. Piper is a test fixture, not a dependency; nothing was added to
`pubspec.yaml`, and no cloud STT or TTS is involved anywhere in this run.

The laptop's own microphone, recorded while `paplay` ran, measured the phrase
at `mean -18.7 dB / max 0.0 dB`, so the room really did get the sound.

## What the phone reported

```
19:47:12  NexusInstaller: speech: listening on-device (no network)
19:47:12  NexusInstaller: speech: …What time is it
19:47:13  RecognitionClient: #onResults withSpeech: true
19:47:13  NexusInstaller: speech: heard "What time is it" (peak 10.0dB)
19:47:13  TextToSpeech: getHighestRankedPublicEngineName = com.google.android.tts
19:47:13  TextToSpeech: Sucessfully bound to com.google.android.tts
19:47:13  TextToSpeech: Connected to TTS engine
```

- **The recognizer was the on-device one** — the path with no network in it at
  all — because the ROM has a local model, which `isOnDeviceRecognitionAvailable`
  reports before the session starts.
- **The transcript is what was said**: "What time is it", from audio that
  travelled laptop speaker → room → phone microphone. Nothing was typed.
- **The reply was handed to the system speech engine** and the exchange ran
  through the ordinary pipeline (the answer card was "It's 19:47").
- The listening state on screen, the pill wearing the accent ring with the stop
  control where the mic was: [shots-20261010/10-voice-listening-ring.png](shots-20261010/10-voice-listening-ring.png)

A first attempt is worth recording too: with the phrase played at 100% sink
volume, the recognizer answered
`nothing recognized (error 7, peak 6.6400003dB)` — it heard the room and found
no words in it. Raising the sink to 170% took the same phrase to `peak 10.0dB`
and a real transcript. That peak field was added for exactly this reason: a
silent room and a dead microphone are the same `null` without it.

## What could not be finished

Everything below is **not** verified, because the phone left the USB bus at
19:52 and never came back (`adb devices` empty, no Samsung device on `lsusb`).
It disappeared immediately after `adb shell cmd connectivity airplane-mode
enable` was issued for the offline test — I cannot say whether the radio toggle
dropped the USB link, rebooted the phone, or something else; no further
command of mine reached it.

1. **The offline run.** The intent was the same sentence with airplane mode on,
   which would have turned "the recognizer is the on-device one" into "and it
   produced that transcript with no network". Not run.
2. **The end-to-end spoken file fetch on the device.** The phrase was generated
   (`"get report dot pdf from my pc"`), but no fetch was ever spoken into the
   phone. Covered headless instead: `test/assistant_view_test.dart` runs the
   spoken form through the real interpreter and executor and asserts
   `fileFetch` with `filename: report.pdf` against the paired PC.
3. **The second-tap stop on the device.** Covered by widget test only.
4. **Audible confirmation.** The engine bound and the utterance was handed to
   it; I have no ears, so "the phone spoke the confirmation" is not something
   this run can claim. `speak` resolving true means queued, not heard.
5. **The screen recording** (`screenrecord` → `adb pull`) the pass asked for.

The APK installed for the run was built before the spoken-filename rewrite
(`spokenToWritten`) landed; that rewrite is covered by tests, and the final tree
still builds a release APK (`flutter build apk --release`, 73.5 MB, 20:12), but
it could not be installed for a second device run.
